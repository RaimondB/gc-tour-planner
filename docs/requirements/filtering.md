# Requirements — Filtering

Hard filters narrow the candidate set; soft preferences re-rank without exclusion. See [design/data-model.md](../design/data-model.md) for how these flow into SQL.

- **FR-F1.** Search caches by center + radius (m).
- **FR-F2.** **Hard filter** on cache type (Traditional, Multi, Mystery, Letterbox, EarthCache, …).
- **FR-F3.** **Hard filter** on Groundspeak attributes (AND-of-OR groups, e.g. `(dog-allowed OR not-stroller) AND wheelchair-accessible`).
- **FR-F4.** Allow promoting any attribute from hard filter to **soft preference** with a positive or negative weight.
- **FR-F5.** **Soft preference** on OSM landuse kinds — predefined system profiles (e.g. "Forest hike day", "Urban evening stroll") plus user-owned custom profiles with per-kind weights.
- **FR-F6.** **Soft preference** on terrain and difficulty target values (with tolerance + weight).
- **FR-F7.** Filter results render on the map with debounced re-query as the user changes filters.
- **FR-F8 (exclude my finds).** The user can toggle a "Exclude caches I have found" filter. When enabled, every cache the current user has logged as found is omitted from results _and_ from the tour-planning pool. Found caches that are still shown (toggle off) are visually dimmed so the user can tell at a glance.

## Smart filtering & planner tool-awareness (PR3)

Layered onto the FR-F* set above; uses the `FR-SF*` prefix to avoid colliding with the existing numbering.

- **FR-SF1 (Multi sub-type derivation).** `CacheDTO` gains `stageCount: number` (count of `additional_waypoints` rows with `type='stages'` per cache). Computed via a sibling subquery in `caches.repository.ts`; no migration. `MULTI_MINI_MAX_STAGES = 2` is the threshold helper that classifies a Multi as a _mini-multi_ (essentially a single hop after the start coord) vs a _full multi_ (3+ real legs).
- **FR-SF2 (Multi sub-filter UX).** `SearchParams.multiSubtype: "all" | "field-puzzle" | "mini" | "full"` (default `"all"`) → `CachesQuery.multiSubtype`. When the `Multi` chip is selected in the type filter, a nested radio appears. Applied **server-side** (in `CachesRepository.find`, post-projection via `classifyMulti(stageCount)`) — see **FR-SF10** for why it moved off the client. Buckets, classified by `classifyMulti(stageCount)`:

  - **field-puzzle** (`stageCount === 0`) — the PQ shipped no `stages` waypoints. Strong signal that the owner expects you to compute the next coord _on-site_ via a field puzzle / formula at the start coord. Different planning profile from the other two: same fixed point on the map, but the on-site effort is puzzle-solving rather than walking sub-waypoints.
  - **mini** (1–2 stages) — quick hop after the start coord; planning-wise close to a Traditional.
  - **full** (3+ stages) — real legwork between sub-waypoints.

  The popup labels Multi caches accordingly: `Field-puzzle multi (no stage waypoints)`, `Mini-multi (N stage(s))`, or `Full multi (N stages)`.

- **FR-SF3 (Curated attribute lookup).** `packages/shared/src/caches/attributes.ts` holds `GC_ATTRIBUTES` — id → human name + iconKey + isTool flag, empirically grounded in the user's real PQ data. `TOOL_ATTRIBUTE_IDS = {3, 4, 5, 11, 12, 44, 48, 49, 50, 51, 64}` is the canonical "needs equipment" set (climbing gear / boat / scuba / wading / swimming / flashlight / UV light / snowshoes / cross-country skis / special tool / tree climbing). Unknown ids render as a generic `?` chip.
- **FR-SF4 (Attribute chips in cache popup).** The popup renders a row of certain-attribute chips (orange tint for tool ids, neutral for the rest) and, below it, a row of _soft_ description-hint chips (italic, dashed border) when FR-SF8 matched anything. Tooltip on the hint row explains "inferred from cache description — may be inaccurate."
- **FR-SF5 (Tool indicator on tour stops).** TourLayer adds a `gctp-tour-stops-tool` symbol layer rendered as a small green-haloed "T" badge to the upper-right of the numbered stop circle, filtered by `hasTool = 1` on the stop feature. The flag combines `attributeIds` ∩ `TOOL_ATTRIBUTE_IDS` with any non-empty `descriptionHints` via the shared `hasToolRequirement` helper, so the on-map indicator and the planner's bonus stay in lockstep.
- **FR-SF6 (Filter: hide tool-required).** `SearchParams.hideToolCaches: boolean` (default `false`) → `CachesQuery.hideToolCaches`. Drops caches where `hasToolRequirement(attributeIds, descriptionHints)` is true. Applied **server-side** (`CachesRepository.find`, post-projection) — see **FR-SF10**. Lives in the FilterSidebar's "Equipment" fieldset.
- **FR-SF7 (Tool bonus on visit-time estimate).** `PlanLoopInput.toolBonusMinutes: number` (zod `.int().nonnegative().max(60).default(5)`). Both planners (greedy + solver) add `toolBonusMinutes` to `result.totals.visitMinutes` per cache that satisfies `hasToolRequirement`. The solver keeps its internal `visitSecondsPerCache` flat for OR-tools optimization (~3-5% effect) but returns the bonus-inclusive totals.
- **FR-SF8 (Description-keyword tool hints, multilingual).** Attribute 51 ("Special tool required") tells the user _something_ is needed but never _what_. The parser scans `<groundspeak:short_description>` + `<groundspeak:long_description>` text against a small curated dictionary (`packages/shared/src/caches/description-hints.ts`) covering en/nl/de keywords for `fishingRod` (incl. "hengel" / "vishengel" / "visstok" / "Angelrute"), `binoculars` ("verrekijker" / "Fernglas"), `magnet`, `tweezers` ("pincet" / "Pinzette"), `ladder` ("leiter"), `mirror` ("spiegel"). Matched hint keys are persisted on `caches.description_hints TEXT[]` (migration `1779670000000`). Three-state nullability: `NULL` = pre-PR3 (back-fill via `POST /admin/uploads/:id/reprocess`), `'{}'` = scanned with no hits, non-empty = scanned with hits. The hints feed `hasToolRequirement` so a description-only fishing-rod cache also gets the orange chip, the green T badge on the tour stop, and the `+5 min` visit bonus.
- **FR-SF10 (Layer consistency — visible set == planner pool).** Whatever the map shows after filtering is _exactly_ what the tour planner clusters. There is one filter definition, applied server-side in `CachesRepository.find`; both the map's `GET /caches` and the planner's discovery pool (`prepareClusteringContext` → `CachesService.list`) run it. Consequently every map filter is a server param: `types`, `attributes`, `contexts`, `excludeFound`, `includeDisabled`, `solvedMysteriesOnly` (FR-SF9), `multiSubtype` (FR-SF2) and `hideToolCaches` (FR-SF6) — the last two were moved off the client for this reason, so toggling them now triggers a (debounced) refetch instead of an instant client filter. The planner forwards them via `PlanInput.hardFilters`. The **one deliberate exception** is `excludeFound`: the pool always forces it `true` (you never plan a tour to caches you've already found), even when the map is showing found caches dimmed. Guarded by `cluster-pool-consistency.integration.spec.ts`, which asserts the discovery pool equals `find()` for the same filters.
- **FR-SF9 (Filter: only solved mysteries).** `SearchParams.solvedMysteriesOnly: boolean` (default `false`) → `CachesQuery.solvedMysteriesOnly`. Unlike the client-side `hideToolCaches`/`multiSubtype` toggles, this is a **server-side hard filter** (it changes the SQL, so it's part of the debounced query input / React Query key): `caches.repository.find` adds `WHERE NOT (type='Mystery' AND solved=false)` — Mystery caches without a solved coordinate are dropped, every other type is unaffected. Served by the partial index `caches_owner_solved_idx (owner_id) WHERE solved`. `CacheSummaryDTO`/`CacheDTO` gain `solved: boolean` so the map badges solved caches with a gold ring; `CacheDTO` also exposes `postedLocation` (the original posted coord) for the popup's "remove solved coordinates" action. Solved coordinates are populated by the [FR-I13](ingest.md) `solvedCoordinates` upload.
