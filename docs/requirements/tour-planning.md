# Requirements — Tour planning

Cluster discovery, routed loop, parking selection. Algorithm in [design/tour-planning.md](../design/tour-planning.md); strategy interface in [ADR-0002](../adr/0002-planner-strategy-interface.md).

- **FR-T1.** Given (center, radius, hard filters, soft preferences, budgets), return a ranked list of **candidate clusters** suitable for a closed loop.
- **FR-T2.** For a chosen cluster, return a **planned loop**: ordered cache list, polyline along walking roads (OSRM), totals (meters, seconds, in-cache-visit time), and parking point.
- **FR-T3.** Budgets the user can set: `maxCaches` (default 15, cap 50), `distanceBudgetMeters` (default 8 000, cap 25 000), optional `timeBudgetMinutes` (using OSRM seconds + per-cache visit time, default 5 min/cache).
- **FR-T4.** Parking is selected by a per-plan `startPreference`. The default is `"auto"`, an _explicit ordered chain_; the single-source modes still do **not** chain among themselves (each only falls back to the cluster centroid, flagged — see below):
  - `"auto"` (default) — try sources in order **`parking-waypoint` → `osm-parking` → `osrm-nearest-road`** and use the **first** that yields a feasible start (one reachable within `maxLinkMeters`). Auto reuses the OSM access/fee filter defaults (`{yes, customers}` / `any`); it does not expose them in the UI. Falls back to the cluster centroid when every source comes up empty.
  - `"parking-waypoint"` — Groundspeak parking waypoint nearest the cluster centroid.
  - `"osm-parking"` (ADR-0011) — OSM `amenity=parking` facility from the `parking_facilities` table, filtered by `osmParkingAccessFilter` (default `{yes, customers}`; `permit` is opt-in) and `osmParkingFeeFilter` (`free | paid | any`). The planner OSRM-walks each candidate to the cluster's nearest cache and picks the shortest within `maxLinkMeters`.
  - `"osrm-nearest-road"` — cluster centroid snapped to the nearest walkable road.
  - `"user-supplied-point"` — explicit `userSuppliedStart`, set by the user **clicking the map** to pick a start point (the web client no longer auto-fills the search center).
  - **No-parking signal.** When no feasible parking is found within `maxLinkMeters` (Auto exhausted every source, or an explicit mode found nothing reachable) the planner still produces a tour starting at the cluster centroid and sets `ParkingChoice.fallback = true`. The web client renders this as a distinct red **"P?"** marker so the user clearly sees that no real parking was found.
- **FR-T8.** Fringe trim (post-leg-pick). After the loop-aware leg picker has tried OSRM alternatives, the planner computes a _retrace overlap_ per cache (meters of leg-in geometry shared with leg-out via a 25 m hash grid). Any cache whose retrace exceeds `fringeTrimMeters` (default 500, range 100–3000) is dropped, the survivors are re-2-optimised, and legs are rebuilt — up to 3 iterations. Coherent loop detours have ~0 overlap and survive; true cul-de-sac spurs have overlap ≈ 2 × spur length and get trimmed.
- **FR-T9.** Pass-1 returns `topNClusters` ranked candidates (sidebar slider, default 5, max 20). The constant cap was removed so a large search area can surface more alternatives without redeploys.
- **FR-T10 (Landuse-weighted soft preference, M5-β).** The cluster `softPreferences.landuseProfileId` resolves against `landuse_profiles` to a set of preferred kinds; the cluster scoring `landuseMatch` term then credits caches sitting inside a `landuse_polygons` row of one of those kinds (`cache_landuse` join). Three system profiles ship seeded: forest-heavy, urban, balanced. Users see system + their own; per-user create/delete UI is deferred. Selecting "(no preference)" zeroes the term out, matching pre-M5-β behaviour.
- **FR-T5.** Return a **score breakdown** per soft constraint so the user understands why the loop scored as it did.
- **FR-T6.** Tour-planning is a pluggable strategy — see [ADR-0002](../adr/0002-planner-strategy-interface.md). MVP ships `GreedyTspPlanner` (DBSCAN → NN+2-opt); solver-based strategies plug in later.
- **FR-T7 (warm-cache reads).** Pass-1 cluster discovery reads walking distances from `route_legs` warmed by the upload-triggered precompute (FR-I8) — Pass 1 must not block on OSRM `/table` calls when the matching pairs are already cached. On a cold cache (no precompute job has run yet, e.g. a freshly-bootstrapped DB) the planner falls back to inline `/table` calls as today; the precompute is an optimization, not a correctness requirement.
- **FR-T11 (Manual plan editing — leg swap).** After a tour is planned, the user can toggle "Edit tour" in PlannerSidebar to swap any leg's geometry for one of the OSRM alternatives the loop-aware picker already considered (no extra OSRM calls). Clicking a leg on the map opens a per-leg panel listing every alternative with meters/min; hovering previews the geometry, "Apply" commits the pick. The displayed polyline, totals, and GPX track export all reflect the picks; the GPX route export is unchanged (route points are the cache list, not geometry). Picks persist in `localStorage` keyed by a stable `planSignature` (FNV-1a over `orderedCacheIds` + parking coords rounded to ~1 m) — reloading restores them, replanning the same cluster restores them, replanning a different cluster does not apply them. Picks are surfaced in the JSON export under `manualEdits.legPicks[]` with the original + picked alternative index per leg, for offline analysis of where OSRM's picker disagreed with the user. Solver-path plans expose no alternatives; the UI degrades gracefully (toggle disabled).
- **FR-T11.1 (Live-drag via-waypoint).** Within the leg-edit panel, the user can press "Add via-point" to drop a draggable marker on the leg's arclength-midpoint. The marker is grabbable; while dragging, the planner backend's `POST /tours/legs/via-route` endpoint (live OSRM `from → via → to`) is called with the cursor's current position, throttled trailing-edge at ~60 ms with at most one request in flight and an `AbortController` cancelling stale responses. The leg's polyline updates live as the marker moves. On mouseup the final route is committed to `legPicks[legIndex] = { kind: "via", via: [lng,lat], meters, seconds, geometry }`, which persists in `localStorage` like the alt-swap picks — reloading restores the via geometry without re-hitting OSRM. NoRoute responses (the user dragged into a pond / private land) keep the last successful preview on screen and tint the marker red; transient network errors do not lose the prior commit. Solver-path plans (no `legs[]`) hide the via-point UI by virtue of the panel being unreachable. The via-point endpoint does **not** populate `route_legs` — every drag position is unique, so caching is moot, and we don't want to pollute the cache with `(from, to)` rows whose stored geometry depends on an ephemeral via.
